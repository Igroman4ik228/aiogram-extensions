# Дорожная карта разработчика

Цель — выпустить проверяемый MVP `aiogram-extensions` по [ТЗ](TZ.md). ТЗ определяет требования, эта карта — порядок работ и условия перехода между этапами. Чекбокс отмечается только после выполнения критерия готовности.

**Исходное состояние до этапа 0 (8 ноября 2026):** есть каркас `src` с демонстрационной функцией и `py.typed`; функциональные модули, тесты и CI отсутствуют. В `pyproject.toml` указаны Python ≥3.14, пустые зависимости и ссылка на отсутствующий корневой `README.md`; `docs/README.md` пуст. Версия `0.1.0` в метаданных ещё не означает готовность релиза.

**Приоритет:** сначала проверить технические риски, затем закрепить контракты и реализовать модули, после — принять MVP целиком. Тесты, примеры и документация создаются вместе с каждой возможностью. Оценивать сроки следует после этапа 1; сейчас они не подтверждены объёмом реализации.

## 1. Технический spike — блокирующие решения

- [x] На закреплённых версиях aiogram, Taskiq, taskiq-redis и Redis собрать минимальную цепочку: отдельный producer → `RedisStreamBroker` → отдельный worker → подставной Telegram API. Проверить публичные точки расширения и Python-совместимость.
- [x] Воспроизвести hard kill до отправки, во время обработки и после успешной отправки до acknowledgement. Проверить pending entries, reclaim/`XAUTOCLAIM`, `idle_timeout`, длинную задачу и работу нескольких workers; зафиксировать потери и дубли в каждом сценарии.
- [x] Проверить retry при временной ошибке и `TelegramRetryAfter`, предел попыток, переход в DLQ и replay. Установить, кто отвечает за retries/recovery/acknowledgements, чтобы эти механизмы не конфликтовали.
- [x] Проверить Bot factory и lifecycle в worker, разделение Redis clients/pools, сериализацию всех обязательных send-методов и медиа. Живой Bot не передаётся через Redis; локальные пути требуют доступа из worker.
- [x] Сохранить в `docs` отчёт: версии и окружение, команды воспроизведения, наблюдения, подтверждённые гарантии, ограничения и решение о выбранном стеке.

**Готово, когда:** критические сценарии воспроизводятся, а выбранный стек позволяет выполнить требования MVP. Если recovery или DLQ не обеспечены, согласовать изменение стека/ТЗ до основной реализации Redis-очереди. Не подменять неудачный эксперимент обещанием at-least-once.

**Выполнено:** 51 тест на каждой версии Python 3.11–3.14 — 204 успешные проверки. Закреплён исправленный wheel `taskiq-redis==1.2.4+aiogramext.2`; recovery, устойчивые retries, DLQ/replay и ограничения подтверждены в [отчёте spike](redis-queue-spike.md). Переход к проектированию контрактов возможен в описанном профиле; exactly-once не обещается.

## Зависимости и дальнейшее развитие

Критический путь: **0 → 1 → 2 → 4 → 5 → 6 → 7**. После этапа 2 пагинацию можно делать независимо от limiter и очередей; этап 3 также обязателен к приёмке. События и проверки сопровождают реализацию, а не откладываются на финал.

После MVP, по подтверждённой потребности: расширенное fault injection и нагрузочные/regression benchmarks; затем Token/Leaky Bucket, adaptive/weighted limits, monitoring exporters, caching и дополнительные helpers. Универсальная очередь задач, новые модули и Python 3.15 требуют отдельной проверки совместимости и объёма работ. Ни один из этих пунктов не расширяет текущий MVP автоматически.
